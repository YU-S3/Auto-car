# 当前软件对第21届疯狂电路规则的专项检查

日期：2026-11-14。检查起点为本仓库提交`9c27dd9`；被检查车载源码仍为Soberup固定上游提交`7abfdac0d0156576ba5186716a7c1e42992359ca`。本次复核只更新报告，不改上游固件。

## 1. 判定

**当前不通过本项目的软件就绪验收，不能认定为可直接参加本车比赛的达标固件。** 已有完整的参考感知—状态—控制链；明确存在本车驱动未适配、原赛道路线未替换、约13秒固定停车等缺口，另外缺少本车构建、图像和实际跑图证据。这个判定不等于已经实测发现每次比赛均失败，也不等于作者原车没有完赛能力。

本工作区当前只有资料、完整上游快照及下载校验脚本，未发现独立本车应用、PC回放/仿真实现、ADS链接产物或实车报告。GCC在PATH可用，但未据此声称已能编译TriCore车载工程；本轮没有运行车载代码或做ADS构建。

采用[第21届规则补充基线](../research/2026-11-14-national21-rule-baseline.md)：文杰杯明确的三科安排保留；全国后期流程的科目三、现场任务，以及国赛75%门槛分别检查，不能混为一个版本。硬件自制资格另见[总体评估](2026-11-14-finish-readiness.md)，不计入本次软件缺陷数。

## 2. 规则不能额外推导出的软件要求

这次明确收窄此前评估中容易误解的表述：

- **不要求车端识别每个元件名称或实现唯一ID系统。** 外部裁判统计实际经过的元件。车端可通过预设路线完成覆盖；离线人工核对路线与元件集合也是证据途径。
- **不要求车端实现计分器、称重换算或75%实时计数器。** 它们可放PC/仿真裁判端。正式路线必须实际满足门槛，不是一定要有某个名为`coverage`的函数。
- **不强制在线最优规划、神经网络或专门的视觉起点识别。** 已公开地图上的固定路线可用；可靠执行到真实发车区、正确触发现场计时并满足通过次数限制即可。需要证明实际行为，不能单凭函数名判断。
- **不强制车轮倒转、地图上两个方向都能运行或自动停车模块的特定实现。** 它们取决于选定路线与现场任务；当前负轮速接口问题属于条件性工程缺陷。
- **不要求车端识别电子锥桶才能合规。** 即使没有边界识别模块，只要实际不接触禁入标志，也可以满足行为条件；反之丢线保护存在也不等于不会撞路肩。

因此，本次不会以“缺元件分类器/全局规划器/计分模块”直接判违规，也不会因无线串口初始化就认定远程操控。

## 4. 可定位的软件问题

P1表示优先解决的功能或可靠性问题；P2为条件性功能/配置风险。全部未修复。这里是源码问题清单，不把每项都称为赛事明确禁止条款。

| 编号 | 优先级 | 精确位置 | 发现、触发条件和影响 |
| --- | --- | --- | --- |
| SW01 | P1 | `initialize.c:27`、`MahonyAHRS.c:150`、`motor.h:33` | 实际依赖RC设备接口及原P33电机映射，本车为RB、接线待核。属于本车部署缺口，不是断言原工程必然编译失败 |
| SW02 | P1 | `route_config.h:12`、`route_config.c:202`、`state_control.c:419`、`menu_tree.c:177` | 原地图路口阈值与路线表未按本校地图替换；菜单仅选subject2/3四条方向路线。不能证明本车实际返回或覆盖，不等于规则禁止预存表 |
| SW03 | P1 | `cpu0_main.c:64`、SDK `zf_driver_timer.c:58` | 10ns计数除以1e8，达到13即停。合法路线若超过约13秒，会提前退出；若某原路线更短，此限制未必触发 |
| SW04 | P1 | SDK `zf_device_mt9v03x.c:243/276`、`image.c:478`、`cpu1_main.c:13` | DMA完成置flag后停采，但下一VSYNC直接重新使能DMA，未等待CPU1释放同一个`mt9v03x_image`。阈值/二值化若与下一采集重叠，会读到跨帧数据；存在实际写读交接缺口，撕裂频率未测 |
| SW05 | P1 | `line.c:209/212`、`isr.c:50`、`motor.h:19` | CPU1先将共享`error`清零再计算，控制读方可看到过渡值；结果无帧年龄契约。视觉停更时已有丢线计数也可能停止更新，控制继续使用旧偏差 |
| SW06 | P1，启用纠偏时 | `cpu1_main.c:14`、`route_progress.c:340`、`run_features.c:5` | 正式跑车环注释掉每帧进度更新；菜单预览却调用。开启里程纠偏时不能证明窗口推进正确；默认关闭，不能据此判默认循线必然失败 |
| SW07 | P1 | `menu_pages.c:270`、`initialize.c:68/103`、`inertial_navigation.c:418` | 菜单已初始化INS/状态后放行；CPU0发布start_flag后闪灯，再次INS_Init和Motor_Reset_State，CPU1可能已推进视觉状态。问题是放行后重复重置，不是INS首次完全未初始化 |
| SW08 | P1 | `motor.c:664/677`、`maze.c:724`、`isr.c:50` | 保护调用可进入含500ms延时的car_stop。电机/NSLEEP先关闭，但执行线程/ISR仍阻塞，影响嵌套中断、日志和状态一致性 |
| SW09 | P2，需倒转时 | `motor.c:344/374`、`motor.c:563` | 上层轮目标可为负，下层负PWM方向分支被注释，非正输出置零。不能宣称完整双向轮驱动；`route_direction=REVERSE`表示反向路线，不代表轮子倒转实现 |
| SW10 | P1，本车迁移时 | `encoder.c:18/44/69`、`initialize.c:105`、`state_control.c:50`、`dashedline_makeup.c:7/22/38` | 5ms注释与2ms调用不符；负数统一加0.5取整有偏；轮计数毫米换算和相机16cm像素表属于原车。未重标定可能造成路口时机、速度和补线错误 |

SW04和SW05分别涉及执行集成与并发可靠性；SW02和SW06涉及任务推进与配置边界；SW07/08涉及启动/终止生命周期。它们不是重复缺陷，需分别验收。

其他已核实的默认值：`record_enable=1`，速度规划和路口纠偏默认0（Flash/菜单可能改变运行设置）；`FORK_ENTRY_DEBOUNCE=0`、`FORK_REENTRY_DELAY_FRAMES=0`；四个`ROUTE_ACTUAL_FORK_*`为0，禁用的是对应角度参考校验，不是将停车阈值置0。默认值说明部分保护需要验证，不能直接推断每个路口都会误计。

## 5. 内存和时序不能直接判通过

按目标TriCore的32位int、`Point`8B和上游轨迹点固定8B进行静态部分估算：

| 已定义对象 | 大小 |
| --- | ---: |
| 摄像头采集图188×120 | 22560B |
| 二值图188×120 | 22560B |
| `Path_Memory[3072]` | 24576B |
| `Side_L/Side_R/cross_backup_L/cross_backup_R`各300点 | 共9600B |
| 上述小计 | 79296B |

**这不是完整RAM占用**：还没计入其他工作数组、路线/事件、Flash缓冲、SDK、栈和CSA。若直接增加一张22560B快照，上述小计即101856B，已比96KB算法桶多3552B。此前8192B点集桶为目标重构预算，不能误称它能容纳原样四个点集；首版需要移除/缩减非必要轨迹或重新分配，不能扩大240KB总规格。

当前源码轮速500Hz、方向约250Hz、相机配置目标100FPS；驱动实际FPS仍需实测。这与本车设计目标视觉30Hz、控制200Hz不同。改变采样周期需重新确定控制与滤波参数，不是把定时器数字改掉即达标。PC平均耗时不能替代TC264最坏耗时，也没有证据表明必须用双核才能完成。
