# 文杰杯疯狂电路组软件算法 Implementation Plan

**Goal:** 用车载摄像头完成电路图赛道的循迹、元器件穿越、支路选择与返回发车区，先逐科稳定完赛，再提高元器件覆盖率和速度。

**Architecture:** 厂商 BSP 负责采集和执行，C 语言算法核心负责视觉、事件、状态机、路线及控制。PC 端负责数据回放和规划对照；比赛运行不依赖 PC。输入图像、输出控制指令及日志使用明确的时间戳和有效性标记。

**Tech Stack:** TC264_BTB/TC264D、MT9V034 188×120、130双电机差速、DRV8701E、双编码器、IMU660RB、IPS114；ADS与逐飞TC264库，C99/C11兼容子集；PC端Python/NumPy/OpenCV/pytest，NetworkX仅作规划对照。纯C核心在PC与MCU共用，首版不引入RTOS。

**文档日期：** 2026-11-13，已按硬件v0.3更新。**状态：** 方案已获用户认可；[Soberup源码基线](../../../soberup/README.md)已下载并校验，本车主应用和回放工具尚未实现。下文计划新增的应用文件和命令仍需逐项实现。板级适配先执行[TC264补充计划](2026-11-13-tc264-v03-porting-plan.md)，硬件型号和保守资源预算见[硬件型号文档](../../hardware-components.md)，官方接口和待标定项见[硬件开发核验](../../hardware-profile.md)。

**依据：** [资料调研与来源清单](../../research/2026-11-13-视觉组资料调研.md)，特别是 PPT 第11—14页及第13页原始公式图片。

## 1. 成绩目标和开发优先级

按宣讲版本，单科 `T = T1 + T2 + 30*(M-N)`，`N>=2` 才满足基本数量条件；仍须返回发车区并遵守其他规则。三个科目成绩累加，未完成/放弃的科目记 278 秒。

同一辆车的重量不变时，先优化 `T1 + 30*(M-N)`。在两条路线均能合法完赛且同等可靠的前提下，多花 8 秒通过一个此前遗漏的元器件，成绩改善 22 秒；多花 35 秒仅增加一个元器件，成绩恶化 5 秒。这个比较必须包括绕行和返回的全部增量时间。

优先级：

1. P0：电机可控、采图可靠、单回路稳定闭合、有效通过至少两个元器件。
2. P1：断线/符号区穿越、直角弯、普通 T 路口、正确回到起点。
3. P2：三端器件分支、并联覆盖、去重和防循环、复杂科目合法保底路线。
4. P3：完整覆盖、代价优化、分段提速、必要时增加模型识别。

路线计算把重复穿越时间算入成本，但元器件奖励按唯一 ID 去重。重复计数的最终裁判语义仍须核实；未核实前采用不重复奖励的保守策略。

## 4. 数据流、接口与调度

数据流：`摄像头 → 预处理 → 路径/出口/元器件候选 → 事件确认 → 状态机/路线 → 速度与转向 → 执行器`；日志旁路读取各层结果。

接口契约：

| 类型/调用 | 关键内容 |
| --- | --- |
| `Frame` / `board_acquire_frame` | 像素指针、宽高、stride、格式、seq、采集时间戳；release前不可被DMA覆盖 |
| `TrackObservation` / `track_extract` | 近中远中心点、有效位、横向/方向误差、0—1置信度、帧时间戳 |
| `ElementObservation` / `elements_detect` | 元器件区域框、入口/候选出口角、节点候选、观测置信度 |
| `NavEvent` / `events_update` | LINE_LOST、COMPONENT_ENTER/EXIT、NODE_CONFIRMED、START_ZONE等事件，事件ID与时间戳 |
| `NavDecision` / `fsm_update` | 状态、选定出口、目标速度、是否允许短距离跨缺口、停止原因 |
| `MotionCommand` / `follower_update` | 线速度m/s、角速度rad/s；board_port按本车有效轮距转换为左右轮目标速度 |
| `board_apply_command` | 限幅、停机优先级、命令超时检查；低层PI可独立定周期运行 |

图像坐标 x向右、y向下；车辆坐标 X向前、Y向左、正角速度向左。图像右偏转换为车辆右转时角速度应为负，必须用左右偏移测试固定符号。像素误差和米制误差不能混用同一组增益。

视觉按完整新帧更新，控制按固定周期运行。建议初始测试目标为摄像头/视觉30Hz、轮速控制200Hz，均是工程目标，不是已确认硬件性能。若板卡不能达到，先减ROI/分辨率，再按实测延迟降低车速。

控制读取完整观测快照，不读一半写一半的数据；丢帧时允许丢弃旧帧，禁止无界排队。采集/定时中断只完成必要搬运与标记，不在中断中跑视觉、输出整幅图像或等待串口。

## 5. 视觉与元器件穿越算法

### 5.1 采图与阈值

1. 用本车镜头、支架高度和曝光采集直线、弯道、每类元器件、普通T和三端分支的图像；覆盖亮、暗、阴影、反光和运动状态。
2. 比较固定阈值、ROI大津法、分块阈值。在深色底白线场景，阈值后白色为前景；先在有效ROI统计，防止车壳/强反光占据直方图。
3. 从固定曝光基线开始，验证不同光照；若必须自动曝光，限定变化幅度，并记录曝光，避免瞬间变化触发假节点。
4. 首版只去除孤立噪点和很小的孔洞。不要对整幅图做大尺度闭运算来“修好”电容/开关间断，否则可能粘连邻近支路。
5. 校准畸变和透视。首版允许按行使用标定中心及线宽查表；需要米制几何时再导出地面映射，畸变校正应先于平面映射。

参考：调研文档 S5、S9—S11。

### 5.2 白线提取

每个选定扫描行提取全部白色连续区间，过滤长度明显不合理者；按上一帧路径预测距离、相邻行连续性和宽度变化给候选打分。不能把整行所有白点做一次平均：两条平行线路的均值可能位于两线之间。

输出近中远多个中心点；只在有效点足够、连续性足够时给高置信度。直线正常线宽作为随图像行变化的标定量，不能全图只设一个像素线宽。

基线横向误差采用各有效行中心偏差的加权和，方向误差用近远中心连线估计。灯泡/电阻框等双轮廓区域使用进入前方向和可见出口约束，禁止把单侧符号边缘直接当行驶中心。

### 5.3 元器件区处理

把元器件问题分成两类：

- 两端器件：以入口、出口及中间区域为单位穿越。电容、电池、开关可能断线；电感、灯泡、电阻可能出现多边缘。沿入口方向预测出口，结合可见出口修正局部路径。
- 三端器件：必须产生可选出口和端口配对，交给选路；不能盲目按进入方向跨过去。

进入 `COMPONENT_CROSS` 必须有正向区域证据，单纯丢线不够。出口不可见时，只允许在已标定的该类缺口范围内低速短时预测；距离和时间两项都设上限，到限即停车/受控恢复。上限由实际断口、有效视野、制动距离和合法走廊取更严格值，不能直接照搬全国赛尺寸。

若编码器许可，累计穿越里程；否则用视觉运动及保守的时间上限辅助，并降低速度，禁止声称视觉时间估算等同可靠里程计。

COMPONENT_EXIT 需出口稳定重捕获、越过退出门限并经历冷却；内部仅记录“疑似/估计通过”。实际有效通过用裁判检测计数校准，摄像头看到符号不代表车体已触发检测装置。

### 5.4 路口确认

在局部ROI的近、中、远截面或环形边界提取出口方向，将同一出口的白色像素聚类，结合入口方向得到左/前/右或任意角出口。真实路口需要多个方向在多帧中持续，且空间位置随前进合理变化。

首版用几何规则和多帧证据；仍分不清符号内部伪分支时，再在该ROI增加骨架和短分支剪枝。剪枝阈值按本车分辨率和真实引脚标定，不按全图固定长短判断。

事件初始采用3帧中至少2帧确认，再在实车上按最大速度和路口可见时间调整；同时保留时间门限，不能假设帧率永远稳定。转弯后的离开冷却根据节点区域是否离开以及行进距离/视觉位移决定，防止同一路口触发多次。

## 6. 状态机与恢复

| 状态 | 进入/退出条件 | 控制行为 |
| --- | --- | --- |
| IDLE | 人工启动且自检通过后进入FOLLOW | 电机停止，重置本次事件和覆盖状态 |
| FOLLOW | 稳定路径；遇元件或节点候选转下一状态 | 常规循迹，按置信度降速 |
| COMPONENT_CROSS | 区域证据成立；出口重捕获后回FOLLOW | 降速，沿选定端口连线或局部路径穿越 |
| NODE_APPROACH | 节点候选持续；确认后选择出口 | 提前减速，冻结本次节点事件ID |
| TURN | 选定出口；方向和线条重捕获成立后退出 | 有界转向，不用固定延时单独判定转弯完成 |
| REACQUIRE | 转弯/穿越后需要连续稳定观测 | 连续有效观测后回FOLLOW，否则进入RECOVERY |
| RECOVERY | 路径失效或动作超时 | 先停车；只在已确认走廊内有限搜索，失败转STOP |
| RETURN | 覆盖目标完成或剩余时间不足 | 沿合法已知路径回起点，不穿越未知空白 |
| FINISH | 起点身份、驶离后返回、任务阶段均匹配 | 停车并锁定结果 |
| STOP | 急停、数据陈旧、越界风险、恢复失败 | 安全停止，记录原因；不能自动无限重启 |

FINISH 不由“运行若干秒”或“看见一条横线”单独触发。已知地图时以起点附近序列、进入方向和视觉特征共同验证；未知地图时结合起点视觉签名和拓扑闭合证据。起点身份不可靠时不宣布自动完赛。

对组件、路口、转弯分别配置动作超时，记录 `state_enter_time`、`last_valid_frame_time`、`last_progress_time`。防循环监视同一节点/端口组合反复出现且无新增覆盖的情况，超过预定次数后切换返航或停车。

## 7. 路线规划：先确认可用地图条件

### 7.1 图模型

节点表示路口、元器件端口和起终点；边表示实际可行驶的线路段。保存长度/实测耗时、入口/出口方向、允许动作和稳定性。三端器件表示为含多个端口及合法穿越关系的区域，不把内部每根白线直接当独立普通路口。

每个元器件有唯一 `component_id`，可以由多条合法穿越动作触发同一ID。内部估计覆盖集合去重，避免从两个方向通过同一器件重复获益。不同外观相同的器件也必须区分ID。

在线定位使用节点类型、出口角组合、邻近元件序列、来向以及许可情况下的里程信息。重复纹理节点须保留歧义；不能仅因“T路口+左转”相同就合并成同一个节点。

### 7.2 默认可部署策略

科目1：不做复杂全局图优化，按连续路线完成单回路，专注元器件和起点。

科目2：在可信的节点和支路身份上，优先选未覆盖且可返回的支路；使用访问栈/已访问端口及回退路径防循环。所有掉头、折返都必须在校赛允许且本车能合法完成时才加入转移。

科目3：先部署已验证的保底路线。在地图未知或节点身份不可靠时，不承诺完整覆盖；优先走可信闭环并保留返航预算。规则允许预录地图时，再启用下面的已知图方案。

### 7.3 已知地图且允许录入时

PC端验证地图连接、合法转向、返回路径及元器件数量。导出由节点ID、入口端口、出口端口、事件预期和超时组成的动作序列；车上仍用视觉闭环执行，不按定时脚本裸跑。

小图的精确对照：以 `(当前节点, 进入端口, 已覆盖元器件mask)` 为状态，动作耗时为非负边权，用 Dijkstra 求到各个返回终态的最短时间；再比较 `time + 30*(M-popcount(mask))`，排除覆盖不足或不合法的终态。禁止通过在边上直接添加负30奖励后使用普通Dijkstra。

初始只在PC端对 `M<=12` 的测试图启用精确状态搜索，并设状态数量和运行时间上限；即使12个器件也可能产生较多状态，需测量。更大图用启发式覆盖和局部改进，不把指数级搜索直接搬上MCU。

全覆盖且所有边都必须走、无向且转向不受限时，可参考中国邮递员思路。实际任务允许漏器件、含转向约束，通常不满足这些条件。NetworkX `eulerize` 只最小化补边数量，不直接优化加权耗时，不作为最终求解器。

返回路径要计入转向成本。若“发车区只能经过一次”的全国赛条款被校赛采纳，起点只能在最终回程进入，规划中应禁止中途穿越；PPT本身没有明确这条，需确认后开启。

### 7.4 不允许预录且必须在线探索时

保持摄像头局部出口检测，维护有限容量的拓扑图、歧义节点候选和已探索端口。探索策略依赖节点重新识别和可行回退：它是单独的高风险任务，不等于简单写一个DFS就能可靠建图。

预计最大节点/边数由赛道确认后设定，所有数组有容量检查。图溢出、定位冲突、无可信返航路径时停止新增探索，执行可信返航或安全停止。该模式至少增加3—5个实车工作日，不能塞进临赛7日主线且保证全覆盖。

## 8. 控制与速度计划

首版使用横向误差P/PD和方向误差项，输出目标角速度或转角；轮速允许反馈时使用PI，含积分限幅、输出限幅和停机清积分。首轮调试先确认左右电机极性与编码器符号，再调速度环，最后调视觉方向环。

本车已确定差速结构，轮距为B时：`vL = v - omega*B/2`、`vR = v + omega*B/2`。四轮滑移转向需实测有效轮距和打滑，不能把理想公式直接当准确里程计。本项目不实现舵机控制分支，左右轮速度通过独立编码器反馈、PI/PID、PWM和DIR执行。

只有获得可靠米制路径时才增加Pure Pursuit：前视目标为 `(X,Y)`，`kappa=2Y/(X²+Y²)`，再由车体模型映射执行器。纯像素坐标不能直接代入米制公式。直角弯和器件区限制前视长度，防止切进绝缘区。

速度由路段、误差、置信度、可见距离共同限幅；接近节点/断线提前降速。制动约束用 `v*latency + v²/(2*a_brake) + margin <= visible_safe_distance`，其中延迟和减速度均实测。发生输出饱和时优先降低目标速度，避免持续摆动。

## 9. 分阶段实施任务

以下工时按一名软件算法队员、硬件队友能配合、每天约4—6小时有效工作估计；硬件未打通、在线建图和临时改规则另计。每个任务包含可独立检查的小步骤。代码实现另开任务执行，本计划不把示意接口伪装成可直接刷机的完整程序。

### Task 0：规则与硬件基线，0.5天

文件：`docs/hardware-profile.md`、`config/rules.yaml`、`docs/test-protocol.md`。

- [ ] 复核已落档的TC264D/MT9V034/130差速/RB选型，补齐主板V1.1连接、SDK和编译器版本、分区RAM和实际采图格式；执行TC264补充计划H0。
- [ ] 把最新群规则与PPT逐条核对，标注新增/变化的评分、许可传感器和起点规则。
- [ ] 确定已知地图或在线模式，明确首版支持的路线动作。
- [ ] 固定启动/急停方式、试跑记录字段和每科最低目标。

验收：硬件与工具链能一一对应，不存在“STC或英飞凌都差不多”的配置；最终规则尚未发布的字段明确保留宣讲版本和限制。

### Task 1：SDK与数据采集，1—2天

文件：`firmware/vendor/`、`firmware/app/platform/board_port.[ch]`、`tools/capture.py`、`data/raw/`。

- [ ] 原样编译厂商最小例程，记录编译输出和RAM占用。
- [ ] 单独跑摄像头例程，记录分辨率、帧率、seq、采集耗时及图像是否撕裂。
- [ ] 单独跑左右电机低速与停止，核对极性、反馈和命令超时停机。
- [ ] 录制每种基础场景以及至少3种光照的完整会话，保存原始图像和时间戳。
- [ ] 加入电机启停时的采图检查，排查供电噪点、曝光和振动造成的识别变化。

验收：连续采图5分钟无死锁，超时停机有效；只有图像可靠后进入算法调参。没有实车时可用PPT图做格式验证，但不计入感知验收。

### Task 2：回放、标注与C核心测试链，1天

文件：`tools/replay.py`、`tools/evaluate.py`、`tools/host/CMakeLists.txt`、`tests/data/manifest.csv`、`tests/test_vision.py`。

- [ ] manifest记录session、frame、scene、split、标注路径、采集配置。
- [ ] 按会话/地图划分调参与保留验证集，禁止把相邻帧随机分到两边造成泄漏。
- [ ] 标注入口/出口、中心路径、元器件区和路口事件，至少人工核对一遍。
- [ ] PC回放叠加ROI、阈值、中心线、出口、状态、置信度，导出逐帧CSV。
- [ ] 用host构建运行板上同一套C核心，Python仅做对照和可视化；避免只验证Python而遗漏C移植差异。

计划命令：`python tools/replay.py --manifest tests/data/manifest.csv --split validation --output artifacts/replay`；预期生成叠加图/视频与metrics，不启动电机。`cmake -S tools/host -B build/host`、`cmake --build build/host`、`ctest --test-dir build/host -C Release --output-on-failure` 用于C核心，须先选定本机可用C编译器。

### Task 3：普通白线与闭环循迹，2天

文件：`vision/preprocess.[ch]`、`vision/track.[ch]`、`control/follower.[ch]`、`control/speed.[ch]`、`tests/test_control.py`。

- [ ] 先写测试：图像左/右偏移对应正确转向；两条白线不能取到中间空白；全黑/全白输出低置信度。
- [ ] 实现ROI阈值、多行线段及连续路径选择，再用固定样本验证。
- [ ] 实现方向控制和执行器限幅，验证停机时积分和旧命令清除。
- [ ] 低速跑直线、缓弯和直角弯；一次只改变一组增益并写入调参日志。
- [ ] 板上测处理时间、最坏控制抖动与日志影响，按实测限制最高速度。

验收：基础线段数据有效帧比例目标≥95%，定义为中心线在人工走廊内且方向正确；每种弯道低速连续10次不丢线。该指标是项目目标，必须报告样本数和条件。

### Task 4：元器件穿越，2—3天

文件：`vision/elements.[ch]`、`navigation/events.[ch]`、`navigation/fsm.[ch]`、`tests/test_fsm.py`。

- [ ] 测试输入电容断线、开关斜线、灯泡交叉和电感曲线序列，要求不把内部形状当成普通路口。
- [ ] 实现入口锁定、区域识别、出口约束、有限距离/时间跨越。
- [ ] 测试黑暗、遮挡和无出口序列，要求不会无限直冲。
- [ ] 实现通过事件冷却，同一器件退出抖动不得重复记账。
- [ ] 单元素10次试跑，比较车上通过估计与外部裁判检测/人工车体通过记录。

验收：两端器件集合每类10次通过成功目标≥9次；任何无证据丢线都不能进入无限预测。三端器件留给下一任务的分支决策，不按两端器件假处理。

### Task 5：普通路口与三端器件，2—3天

文件：`navigation/events.[ch]`、`navigation/fsm.[ch]`、`vision/elements.[ch]`、`tests/test_fsm.py`。

- [ ] 构造普通T、三端元器件和符号伪分支的成组测试，每组有真阳性和易混淆负例。
- [ ] 实现出口聚类、多帧确认、接近/转向/重捕获和离开冷却。
- [ ] 实现所选出口不可见或不合法时的减速、有限等待和停车。
- [ ] 测试不同速度和来向，测量事件触发是否足够早以完成制动和转弯。
- [ ] 测试连续两个近邻路口，确认冷却不会吞掉第二个事件。

验收：至少30个独立路口事件的召回率目标≥95%，同时报告误触发次数；小样本不宣称统计保证。各允许转向完成10次测试，至少9次成功且无越界。

### Task 6：科目1闭环与起终点，1天

文件：`navigation/fsm.[ch]`、`telemetry/log.[ch]`、`tests/test_fsm.py`。

- [ ] 实现起点签名、驶离确认、返回匹配、阶段约束和完成停车。
- [ ] 回放中途经过相似图形、启动原地看到起点、只通过一个器件等负例，不能误判完成。
- [ ] 按完整科目1路线试跑，记录T1、估计N、检测N、丢线和恢复次数。
- [ ] 保存稳定参数和可恢复的固件构建产物。

验收：科目1连续10次合法完赛，N满足规则；至少覆盖3种训练环境。没有官方计数器时记录人工判定，并明确尚未验证裁判触发。

### Task 7：科目2覆盖，2天

文件：`navigation/topology.[ch]`、`navigation/planner.[ch]`、`tools/plan_route.py`、`tests/test_planner.py`。

- [ ] 为元器件建立唯一ID，测试重复穿越、三端器件多入口只奖一次。
- [ ] 实现选路和返回预算；已知地图模式导出事件动作序列，在线模式维护端口访问及歧义状态。
- [ ] 测试所有路线从起点出发、合法返回、不经过禁用动作；测试无返回路径和图容量溢出。

### Task 8：科目3与路线优化，2—3天

### Task 9：整机回归、冻结与交接，2天

验收目标：每科20次中至少19次合法完赛；这是小样本发布门槛，不是对现场成功率的保证。未达到则降低速度、覆盖目标或算法复杂度，不能删掉失败记录。

| --- | --- | --- |
| ≤3天 | 仅在现有车已能采图/运行时，修复采图、低速循迹、两端器件、合法保底路线和停车 | 不保证从零完成三个科目；推迟建图、模型和全覆盖优化 |

| 约3—4周 | 按Task0—9执行，约17—23个有效工作日，可在等待硬件时做回放工具 | 根据真实进度决定是否加入Pure Pursuit或小模型 |

比赛前最后一天只允许修复已定位的问题与回滚，保留已知可完赛版本，不临时切换未经回归的架构。

## 11. 性能、内存与实验记录

本车以188×120灰度作为初始尺寸：单帧22,560B，采集帧＋只读快照＋uint8二值图合计67,680B，尚不含栈、CSA、SDK、点集和日志。官方当前相机驱动为单图数组，必须完成帧所有权适配，不能把finish_flag当锁。官方50FPS配置、视觉30Hz目标及实测吞吐分开记录。

SRAM总规格统一按240KB记录，保守设计为算法数据≤96KB、SDK/CSA/栈/中断等预留96KB、未分配保护余量48KB。三张图67,680B计入算法桶，点集/直方图/路线与控制状态也在该桶内核算；同时逐区域检查.map，不能把总预算合格当作局部区一定能放下。IPS行刷新，不增加64,800B全屏缓存；不使用两张全图float逆透视表。时间预算以单CPU视觉30Hz、每帧≤15ms为初始目标，实测后调整。

记录每次试跑：`run_id, date, code_version, params_version, rule_version, map_id, light, battery, speed_profile, completed, T1, T2, N_estimated, N_judge, M, score, failure_reason`。N_judge不可获得时记缺失，不能用N_estimated偷偷替换。

板上测量采集到控制指令的端到端延迟及其分布，视觉P95、最坏控制周期、丢帧数、最大队列占用。30Hz目标下，首版视觉耗时目标≤20ms且不挤占控制；达不到则降载/降速并记录实际结果。

开发期可传图，竞赛模式只保留规则允许的低负载日志；非阻塞队列满时丢调试数据并记数，不阻塞控制。
