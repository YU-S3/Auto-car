# 疯狂电路软件分工：算法与硬件接入

日期：2026-11-14。依据：用户要求按比赛规则划分算法、硬件接入两部分，并准备改进工作；本项目已认可的共享C架构、硬件v0.3及[软件专项审计](../../assessment/2026-11-14-software-compliance-audit.md)。本文交付职责与接口设计，不表示已经完成固件改造。

## 1. 目标与采用方案

目标是让两条线可并行交付、独立排错，最后以同一个可构建固件和实际完赛证据验收。算法侧建议由你牵头，接入侧由负责板卡/底盘的队员牵头；不假定具体人数或人员姓名。

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 共享C核心＋板级适配 | PC可先验证；设备变化集中在适配层；分工接口可检查 | 需先拆全局依赖；采用，延续已认可架构 |
| 原Soberup双核工程中按文件分给两人修改 | 初期复制快 | motor、initialize等同时混有算法和设备动作，容易互相覆盖；不作为主方案 |
| 先搭完整机器人框架和高精度仿真再迁移 | 能提前演示整车行为 | 扩大工具链和模型工作，不能替代TC264采集和时序验证；Webots作为后续验证工具 |

首版采用单CPU应用、传统视觉、路线执行与轮速控制。总SRAM240KB；算法数据含采集图≤96KB，系统预留96KB，保护余量48KB。视觉30Hz/≤15ms、控制200Hz/≤0.5ms、显示≤5Hz是待实测的项目目标。源码快照保持不变。

## 2. 比赛任务转为软件工作

技术规则来源见[第21届规则基线](../../research/2026-11-14-national21-rule-baseline.md)，文杰杯三科与全国后期单科/国赛门槛分别记录。

| 必须达成的行为 | 算法侧工作 | 硬件接入侧工作 | 最终证据 |
| --- | --- | --- | --- |
| 本地自主运行 | 视觉→路线→运动指令闭环 | 本地采样和执行，不依赖PC下发运动指令 | 断开PC后完整运行记录 |
| 白线、弯道和元件干扰通过 | 阈值、补线、边界、出口、失效判断 | 稳定灰度图、曝光配置、安装参数与原始帧导出 | 本车回放集和实际通过记录 |
| T口/三端器件与反馈回路 | 分支判断、去抖、路线进度和返回约束 | 时间、轮速、IMU等可靠反馈 | 分支事件日志及路线对照 |
| 满足适用覆盖门槛 | 公开地图路线配置、离线元件覆盖核对 | 执行路线并记录实际传感器/状态 | 裁判N、返回与视频相互一致 |
| 避免绝缘区锥桶/路肩 | 不跨支路误补线，弯道限速和失线策略 | 执行停车、记录尺寸和制动响应 | 完整车体不接触限制标志 |
| 返回发车区 | 证明路线闭合，避免运行中途误穿起点 | 现场发车/结束动作接入及时间记录 | 实际返回触发与完成记录 |
| 现场方向/软件任务（适用时） | 路线/任务配置入口及相应行为 | 按键或规定发车方式、参数装载 | 按实际现场要求演练 |
| 可持续执行到结束 | 保护超时策略、计算量约束 | 调度、看门狗/故障执行、内存布局、低优先级调试 | .map、最长耗时、故障注入结果 |

N≥2是文杰杯PPT/基础阶段门槛；国赛75%口径另验。车端不强制元件名称分类、实时计分或在线最优规划。可以离线人工确认元件集合，并用固定路线达到要求；不能用“没有某个算法模块”直接代替行为验收。

## 3. 主责边界

### A线：算法、策略和PC验证

负责“输入给定数据，应该算出什么”，交付可由PC和TC264共同编译的C99/C11兼容核心：

1. 视觉预处理、二值化、有界补线、边界/中线、出口及有效性；提取image、maze、element_line、dashedline_makeup、line中的可用部分。
2. 路口状态机、进入/退出去抖、路线配置、合法闭合与适用覆盖检查；改造state_control、route_config、route_progress的算法逻辑。
3. 运动学、目标限速、方向控制和左右轮PID/抗饱和；从motor中提取计算，不保留GPIO或PWM调用。
4. 姿态滤波/融合、角度积分和偏差控制的数学逻辑；输入是已转成车体坐标和物理单位的IMU样本。
5. 图像过期、失线、任务超时等决策条件，以及停止后积分/状态复位规则；向平台提出停机请求。
6. PC同源编译、原始帧回放、事件回归、路线核对、控制模型和后续仿真算法适配；分析误检、漏检和控制问题。

不直接编辑SDK、寄存器、中断向量、链接脚本、引脚映射；不在核心刷屏、发送串口或操作Flash。算法负责人对算法内存和执行量负责，不能把超预算全部交给接入侧处理。

### B线：硬件接入、嵌入式运行与实测

负责“怎样取得可信数据、按时运行计算并执行结果”，同样属于软件开发：

1. ADS工程、逐飞官方库版本、板级GPIO/定时器/DMA/SPI/UART资源与链接配置。
2. MT9V034初始化、曝光/增益、188×120采集、完整帧所有权、seq/时戳、错误与掉帧状态、原始图导出。
3. 左右编码器解码、计数位宽/回卷、符号、时间间隔，以及轮径/齿比/count标定和统一单位转换。
4. IMU660RB通信、自检、量程/ODR、单位和安装轴映射，提供静止与转动样本；不再调用RC设备接口。
5. DRV8701E PWM/DIR与使能/制动输出、极性和上限；快速停机动作及必要的命令过期保护。
6. BOOT/SELF_TEST/READY等运行组织、单CPU调度、算法调用、中断、完整观察发布、低优先级显示/日志与Flash装载。
7. .map逐区占用、栈/CSA水位、采样/IRQ/算法耗时和控制抖动测量；提供可复现板上记录。

不在设备驱动里新增路线判断、视觉阈值、分支选择或第二套PID；不使用SDK中同名功能代替未经核对的项目算法实现。

### 容易混淆的工作：必须有唯一主责

| 工作 | 主责 | 配合方与交接 |
| --- | --- | --- |
| PID/方向控制公式与增益配置 | A | B提供周期、阶跃/轮速日志并执行输出；上车调参共同完成 |
| 曝光与相机几何标定 | B负责采集/安装测量，A负责图像尺度参数 | B交原图、安装尺寸和配置；A交补线/ROI参数并做错误样本回归 |
| 编码器counts→m/s | B | A核对单位、正方向和控制器dt；不能两边各转一次 |
| IMU融合与零偏估计逻辑 | A | B提供RB物理量、轴映射和静止数据；标定结果由B纳入本车配置 |
| 任务/视觉失效判据 | A | B按已冻结条件调度执行；底层硬故障可直接关闭驱动 |
| 故障快速关闭电机、ISR不阻塞 | B | A消费锁存故障并复位控制状态；显示和保存延后 |
| 帧所有权与观察发布 | B | A只消费借用只读帧、按约定释放并提交完整结果 |
| 算法源码和PC/板端一致性 | A | B让ADS引用同一目录，提供板端结果和构建宏 |
| 整体固件集成 | B | A交核心、PC验证和算法配置；双方共同验收行为 |
| 完赛覆盖/路线证据 | A | B提供实际运行日志，双方核对外部裁判记录 |

“共同完成”不代表共同随意编辑同一文件：表中主责方提交，另一方提供输入并验收。

## 4. 统一文件范围

下列是拟建路径，本轮不创建源码骨架。当前实际存在的`soberup/upstream/`只读。

| 路径 | 主责 | 内容 |
| --- | --- | --- |
| `src/interfaces/car_types.h` | A维护，B共同验收 | 纯C跨侧类型、单位、状态和版本；不引用SDK |
| `src/core/vision/`、`mission/`、`control/`、`attitude/`、`safety/` | A | 共享算法，静态有界数据 |
| `src/platform/tc264/board_config.h` | B | 唯一引脚/外设映射，未知值不能猜测为可运行配置 |
| `src/platform/tc264/board_port.[ch]`、`app_runtime.[ch]` | B | 驱动适配、采样/执行、时间、帧所有权和运行调度 |
| `firmware/vendor/TC264_Library/`、`firmware/ads/` | B | 锁定官方依赖、ADS工程及包含/链接路径 |
| `host/CMakeLists.txt`、`host/replay/`、`host/sim/`、`tests/` | A | 同源PC构建、回放、模型和必要回归；sim按阶段加入 |
| `config/routes/`、`config/vision/`、`config/control/` | A | 路线、视觉尺度和控制参数 |
| `config/calibration/` | B | 每台车编码器、轮距、IMU轴/偏置、相机实测与输出映射 |
| `docs/validation/` | 按报告主责 | A交算法/路线结果；B交采集、资源与时序；联调共同记录 |

ADS与host都引用`src/core/`，不各拷一份算法。旧计划中的`firmware/app/vision`等、`tools/host`被此路径约定替代；旧计划保留为历史工作内容参考。配置可在PC保存JSON/CSV，再导出或装载为固件C常量；不因此要求MCU实现JSON解析。

## 5. 先冻结的数据契约

沿用架构已有名称，下列为待实现协议，不是当前可调用API。首项交付是双方可独立编译的纯C类型头和文字说明，之后再提取业务源码。

| 数据 | 生产→消费 | 必须包含与约束 |
| --- | --- | --- |
| `FrameView` | B→A | 只读8位灰度、width/height/stride、seq、capture_ms；上限188×120；有效期内不会被DMA覆盖 |
| `WheelSample` | B→A | 左右有符号count增量、采样dt、m/s和累计m、有效标志/序号；向前为正，换算只做一次 |
| `ImuSample` | B→A | 车体坐标角速度rad/s、加速度m/s²、时戳/seq、校准/有效状态；新样本才积分 |
| `VisionObservation` | A→任务/控制，B负责发布 | 帧时戳/seq、valid、偏差px/角度rad、出口及置信度；一次完整发布，禁止中途清零对读方可见 |
| `MissionCommand` | A任务→A控制 | 科目/规则口径、路线步骤、v(m/s)、omega(rad/s)、停止/限速状态 |
| `MotorCommand` | A控制→B | 左右归一化有符号输出[-1,1]及使能；B完成PWM/DIR；未验证反向时不能静默接受反向需求 |
| `RunRecord` | 双方→PC记录 | 固件/配置/接口版本、seq/时戳、任务进度、停车原因、耗时/丢帧/控制超期 |

车体x向前、y向左、z向上；正偏航为左转。图像像素坐标x向右、y向下；横向偏差约定“目标线在车左”为正，不能直接把像素x增量当左转。v>0前进、omega>0左转，轮目标`vL=v−omega×B/2`、`vR=v+omega×B/2`；B为有效轮距，不能默认等于机械量尺值。

停止顺序为平台立即关闭输出/使能并锁存原因→核心复位积分与任务→后台显示/保存；A的执行结果不能重新使能已锁存故障。启动顺序为全部采样和核心状态初始化完成→发布READY→发车→不再异步重置。时间使用同一毫秒时基及回卷安全差值。

图像过期阈值、实际采样周期和保护超时由B测量、A给策略后冻结到配置并记录版本；未测量时不宣称已满足安全停车距离。冻结记录必须包含采样周期、最长采集/处理延迟、停机请求至驱动关闭延迟、停止距离和测试速度，缺一项不能升级实车测试速度。

## 6. 哪些先做、哪些后做

优先完成：本车独立驱动与停止、PC同源核心、帧交接、低速循线、匹配本校地图的闭合路线，再验证复杂网络和适用覆盖门槛。

首次接入不保留完整3072点轨迹、不分配IPS完整帧、不照搬N30增益、16cm像素表或原预赛/决赛路口数。已有原样四点集9600B超过目标8192B桶，A要精简或重分配；B用.map复核。国赛75%不是“性能优化”，属于该口径有效性门槛。

后续优化顺序：解决已记录的误检/错叉→提高运行成功率→满足截止期/资源→增加必要覆盖→提高速度和成绩。双核、复杂重定位、精细元件分类、神经网络只在失败证据说明必要时另立任务，不作为开工前置。

具体工作包、SW01—SW10归属及联调门槛见[改进准备计划](../plans/2026-11-14-algorithm-hardware-improvement-plan.md)。当前是可评审分工方案，后续固件实施不以本文中的拟建目录存在为完成证明。
