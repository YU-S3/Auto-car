# Soberup源码结构与阅读指南

对应本地`soberup/upstream/`，锁定main提交`7abfdac0d0156576ba5186716a7c1e42992359ca`。本文根据实际目录和关键调用链整理，不把作者历史文档中的全部功能都当成当前已启用功能。当前是源码阅读结论，不是已编译/实车验证结论。

阅读对象：负责疯狂电路车视觉、路线和控制算法的队员。硬件参考：[本车型号与保守资源](hardware-components.md)。

如果只为理解比赛算法，重点是`code/`；如果想知道“算法什么时候执行、怎样拿到图像、怎样变成PWM”，必须连同`user/`阅读；只有涉及硬件接口和异常时再深入`libraries/`。不需要从英飞凌底层707个文件逐个顺序看起。

`soberup/`外层README和JSON不在小车运行时执行。它们管理来源、复用选择和完整性。`upstream/`中含原工程，并没有把main和inav混在一起。

## 2. 实际运行主线

### 上电与CPU0

入口：[cpu0_main.c:51](../soberup/upstream/user/cpu0_main.c#L51)。CPU0先初始化时钟和调试、无线串口，再调用`init_mian()`。这个函数名就是源码拼写，查找时不要改成`init_main`。

[initialize.c](../soberup/upstream/code/initialize.c)按源码执行屏幕/相机、电机/NSLEEP、编码器、电压、LED、IMU初始化，加载部分Flash参数、进入菜单并等待运行选择，然后设置启动标志、启动负压、初始化轨迹/控制状态和定时器。它不是纯算法初始化，里面有实际硬件动作，不能未经适配就在本车执行。

CPU0主循环还做运行诊断显示、超时停车判断、地图保存提示和速度日志发送。2026-11-14沿SDK计时实现核实：`system_getval()`返回10ns单位数值，主循环除以100000000后以13为阈值，因此约13秒触发固定停车。这不是PPT给出的校赛时限，需要在本车任务层重新制定保护超时；278秒是未完成科目的计分值，也不能直接当超时。

### CPU1视觉流水线

入口：[cpu1_main.c:5](../soberup/upstream/user/cpu1_main.c#L5)。等待`start_flag`，在图像完成且未停车时执行：

```c
int ther = otsuThreshold_fast();
binarization(ther);
Dashedline_Makeup();
search_line_main();
state_update();
caculate_error();
mt9v03x_finish_flag = 0;
```

这几行是第一轮阅读最有价值的“目录”。分别回答：怎样区分白线、怎样修补断线、怎样沿线提取几何、当前是什么路口、应该跟踪哪条线，以及方向偏差多大。

### 定时中断控制

[user/isr.c](../soberup/upstream/user/isr.c)中，CPU0的CCU60_CH0中断调用：

```c
if (record_enable) INS_Record_Trajectory();
combined_control((int)basic_speed, return_error());
```

该通道在初始化中配置2ms，即名义500Hz入口。`combined_control()`里方向控制每两次入口才更新，轮速控制则每次调用，所以不能把“入口500Hz”误写成“全部控制环500Hz”。以实际代码条件为准，相关注释里仍有不一致的旧文字。

另一个CCU60_CH1中断调用`Mahony_GetAngles()`和`state_imu_exit_check_isr()`，IMU初始化也将它配置为2ms。相机采集则依赖设备驱动、DMA和相应中断。

```text
相机/驱动/DMA
  → 原始灰度帧
  → CPU1：阈值 → 二值图 → 补线 → 边界/出口 → 路口状态 → error
  → CPU0定时中断：方向控制 → 左右目标速度 → 轮速闭环 → PWM/DIR
                        ↑                         ↑
                    IMU姿态                    左右编码器
```

**上游当前是双核代码，我们计划的首版是单CPU执行算法。** 这不是矛盾：我们参考上游算法，然后按本车保守预算重新组织调度，不是原样照搬它的两核入口。

## 3. code/：算法队员的核心区域

### 3.1 image.c/h：从灰度图得到二值图

主要入口为`otsuThreshold_fast()`、`binarization()`。原灰度帧来自设备层，二值图为`mt9v03x_image_bin`。这里不仅有基础大津法，还有6×4分块、局部亮度补偿、异常块处理和阈值历史等逻辑。

重点观察输入图是否过曝、白线是否断裂、相邻白图案是否粘连；记录阈值随帧变化，而不是只调一个固定数字。先理解输出图像和失效输入，再研究每一段直方图优化。

移植时应将函数改造成“图像指针＋尺寸/stride＋配置→结果”，不能让PC算法包含MT9V03X驱动头和Tasking段声明。现有源码本身还不是独立PC图像库。

### 3.2 dashedline_makeup.c/h：修补已知范围的线路缺口

在爬线前处理二值图，尝试连接满足横/纵尺度限制的白段。它受路线补线模式和像素尺度表约束，不是无条件把黑区涂白。

对疯狂电路组很重要：电容、开关等会使图案不连续。但补线过强会把不同支路连接起来，造成虚假路口。其标定参考188×120和16cm高度；本车120°镜头和支架高度需要重测，不能把这些数组当普适参数。

### 3.3 maze.c/h：边界爬线，不是全局寻路

`search_line_main()`从近车区域寻找起点，调用左右爬线逻辑，生成`Side_L/Side_R`点集，维护有效点数量、边界出口记录、左右间距趋势，并处理回头爬行、坏线重找和越界保护。

头文件里`Point`只是像素坐标；`ExitRecord`记录爬线经过图像左右/上边界的情况。这里的“出口”首先是图像几何证据，后续再判断是否对应真实赛道路口。

重点看：起点怎么选；爬线何时结束；最大步数；遇到圆形灯泡、电阻框和三端符号时是否误爬；一侧失效时是否还能用另一侧。不要在这里寻找BFS/A*和整张电路图最优路线。

### 3.4 element_line.c/h：把几何证据解释成路口

`count_valid_exits()`结合爬线出口、多层边界记录和白色区域验证筛除伪出口；还包含直角识别和调试显示函数。`state_update()`实际调用`count_valid_exits()`，所以这一模块属于运行视觉链的一部分。

本车重点样本：普通T、三极管等三端器件、灯泡内部交叉、电感弯曲、电阻矩形。我们需要知道“入口/可走出口”，不必先识别每个电气符号的精确型号。

### 3.5 state_control.c/h：决定处于哪个行驶阶段

状态定义包括`normal`、`fork_straight`、`fork_turn`、`fork_exit_pending`，另有直角元素状态。逻辑根据出口证据、路线表、航向变化和可选里程窗口进入或退出路口，并推进路口编号、统计进入退出来源。

重点不是背所有if，而是为每个状态写清楚四项：进入证据、控制目标、退出证据、失败超时。把“看见路口”“选择出口”“完成转弯”“重新捕获线”区分开。

当前源码有固定赛道编号特例、RC姿态反馈、某些防抖/冷却参数为0的设置。它们是原队调车经验，不是我们已经验证的通用规则。

### 3.6 line.c/h：决定跟踪哪条线并计算方向误差

主函数的拼写是`caculate_error()`。它按状态选择前瞻点和左右边界参考点，生成中间参考点，并计算角度式偏差。普通段、直角、三叉直行和三叉转弯可以采用不同跟踪策略；十字处还可能调用`cross_rebuild_edges()`。

重点看`front_point`的意义：这里经常是爬线点集的索引，不直接等于厘米数或图像行号。远瞻会更平稳，但可能切弯；近瞻更灵敏，但更容易抖动。误差的坐标、符号和量纲要与后续控制保持一致。

### 3.7 route_config / route_progress / map_event / trajectory_policy：路线与进度

| 模块 | 负责什么 | 不要误解为 |
| --- | --- | --- |
| `route_config.c/h` | 各赛道/方向的固定转向、出口对、补线和停止编号配置 | 自动生成任意新地图最优路径 |
| `map_event.c/h` | 将记录轨迹中的连续元素区段归并为路口/直角等事件 | 原始图像中的元器件分类器 |
| `route_progress.c/h` | 当前里程、事件游标、入叉/出叉窗口和错位修正 | 已经可靠运行的在线拓扑SLAM |
| `trajectory_policy.c/h` | 元素编码、ID解析和风险对应速度上限 | 整张图的覆盖路线求解器 |

特别留意：CPU1运行入口中`route_progress_begin_frame()`是注释状态，而菜单图像页面有调用。因此“某个函数存在”与“比赛运行主线实际调用它”不同。启用里程窗口相关功能前要跟踪执行路径验证，不能仅依据CODE_SUMMARY认定已经接通。

我们校赛还需补齐元器件唯一ID、重复计数语义、漏件30秒收益、返航约束，以及是否允许预录地图的规则；不能把作者数组换个名字就算完成全局规划。

### 3.8 motor.c/h＋encoder.c/h：从视觉误差到轮子转动

`combined_control()`是主控制入口：读取基础/规划速度，做软启动；方向PD生成左右差速量；限制轮速；调用左右速度闭环；检查保护与负压控制；最后更新里程状态。

重要函数包括`speed_control_L/R()`、`L_set_PWM/R_set_PWM()`和`car_stop()`。编码器负责原始计数、清零、尖峰处理与滤波，控制再用反馈修正输出。

上游的speed数字不是已经定义好的m/s。后续必须先明确“每采样周期的count”与物理轮速的换算，再调PID。40000r电机版本也不能直接填成目标轮速。130电机、轮径和传动比改变后不能沿用N30参数。

`motor.c`还含负压风扇和NSLEEP控制，本车方案没有确认这套原车结构，因此这些输出只作参考。这里名称带motor，但实现包括上层策略，不只是PWM驱动。

### 3.9 MahonyAHRS.c/h：姿态与角速度

读取IMU、去零偏/滤波、执行Mahony姿态解算、提供欧拉角和连续偏航等输出。转弯状态会使用这些反馈。

当前实际调用`imu660rc_*`，本车为IMU660RB，需替换设备适配、重新定采样周期和坐标方向。六轴加速度无法提供绝对航向参考，不能把短时间转弯角估计当成永不漂移的全局方向。

### 3.10 inertial_navigation.c/h：main分支中的里程、速度表与存储

本分支`INS_Update()`主要累加左右轮计数的平均绝对增量、保存yaw与视觉误差；没有据此更新全局x/y坐标。结合其他函数实现轨迹打点、按误差/元素规划速度、路标修正、Flash保存/加载和CRC校验。

`Path_Memory`最多3072点，每点静态检查为8字节，因此仅该数组占24,576B＝24KB。它约占我们96KB算法预算的四分之一；不能因为它在原车可用，就在首版无条件保留全容量。

读它时重点关注用途是否真的需要、轨迹格式、容量、溢出和Flash完整性。先稳定循迹和路口，之后再加入记忆速度表；不要一开始就把全部功能开启。

## 5. user/：调度、入口与中断

`cpu0_main.c`与`cpu1_main.c`分别是两核应用入口，不是两个互不相关的小车程序。CPU1写视觉误差和状态，CPU0控制中断读取它们，两者的数据一致性需要明确设计。

`isr.c`实现实际中断体；`isr_config.h`定义优先级、服务CPU及映射等；`isr.h`提供中断相关声明。看到`IFX_INTERRUPT(...)`应理解为硬件触发，不是普通主循环主动调用。

`cpu0_main.h`是该入口的配套头。判断某个功能是否会执行，需要同时看函数定义、初始化、使能标志、调用位置和中断归属，不能只在目录中找到文件。

CPU0运行诊断显示在源码中按约20ms检查刷新，与我们本车计划的5Hz低负载显示不同。移植时按实测控制截止期重新安排。

## 6. libraries/：按层理解，按需深入

| 子目录 | 实际职责 | 我们的重点 |
| --- | --- | --- |
| `zf_common/` | 公共类型、时钟、FIFO、数学、字体、调试和总头 | 认识uint8/int16等类型与时钟；纯C算法不要依赖整份总头 |
| `zf_driver/` | MCU外设驱动，例如GPIO/PWM、GPT12编码器、DMA/ERU、PIT、SPI、UART和Flash | 板级适配时重点看encoder、PWM、DMA、PIT、SPI；业务算法不直接读寄存器 |
| `zf_device/` | 在外设驱动上封装MT9V03X、IMU660RB/RC、IPS114、无线串口等具体模块 | 我们重点是MT9V03X、RB和IPS114；目录有很多设备不代表本车全在用 |
| `zf_components/` | printf重定向、逐飞助手及接口组件 | 图传/波形/日志调试时阅读，控制中断中避免无界阻塞输出 |
| `infineon_libraries/Configurations/` | 英飞凌底层配置支持 | 目标与构建相关时再核对 |
| `infineon_libraries/iLLD/` | 英飞凌低层驱动库，承接逐飞外设封装 | 外设问题需要时下钻，不作为算法入门第一站 |
| `infineon_libraries/Infra/` | 启动、内核、编译器/基础设施支持 | 不随意删改；启动异常/内存异常时查对应部分 |
| `infineon_libraries/Service/` | iLLD周边服务和板级支持 | 按实际依赖查阅，通常先保留 |
| `doc/` | GPL声明、版本记录 | 版本文件为V3.4.1，不能当成另行核验的官方V3.4.6 |

一个典型设备调用关系：`IMU算法 → zf_device_imu660rb → zf_driver_spi → Infineon iLLD → 芯片寄存器`。这解释了为什么只复制一个姿态C文件通常无法编译。

特别注意`zf_common_headfile.h`：本归档不仅汇总厂商头，还在第122行起引入大量`code/`业务头。很多文件看起来只include一个总头，实际上隐式依赖整车。提取共享C核心时要把依赖逐个显式化。

## 7. 工程文件与链接脚本

- `.project`：ADS/Eclipse识别工程名称、构建器等。
- `.cproject`：编译/链接参数、包含路径、宏、目标相关配置。它不是小车业务逻辑，但缺失会影响构建。
- `.settings/`：ADS/Eclipse工具链和资源编码等偏好；GBK/UTF-8阅读问题需结合文件实际编码，不能批量改原快照。
- `Lcf_Tasking_Tricore_Tc.lsl`：控制代码、静态数组、栈、堆、CSA在内存中的位置。SRAM总规格仍是240KB，但大数组能否放下需要结合实际段布局和.map。

## 8. 给本项目的阅读与实施顺序

第一轮只读`cpu1_main.c`的六步流程、`image.h`、`maze.h`、`state_control.h`、`line.h`：每个模块写出输入、输出和全局依赖。

第二轮读`image → dashedline_makeup → maze → element_line → state_control → line`，使用本车原始帧做分阶段叠加图。先确认图像和路线几何正确，再看闭环控制。

第三轮读`isr.c → combined_control → speed_control_L/R → encoder → L/R_set_PWM`，厘清中断周期、counts/周期、目标速度和PWM的区别，再按130电机调参。

第四轮读`route_config → map_event → route_progress → inertial_navigation`，明确哪些是预存路线，哪些是记录/速度策略，以及我们缺少的全局覆盖功能。

初期不照搬原队GPIO、IMU660RC接口、N30参数、路线编号、负压动作、固定延时和双核组织。保留算法思路，将硬件、配置、时间和日志通过接口传入。原样`upstream/`继续保持校验不变，改造代码放本项目应用层。
